# tp126 时区与时间换算工作台

一个本地小工具：把各地时区连同夏令时规则登记进来，再把某一个时刻换算到所有已登记的时区，页面上直接看出各地是当地的几点、谁的日期已经翻到前一天或者后一天、跟来源时区差了几个小时。时区名写得不合规矩、偏移超出范围、夏令时偏移不比标准偏移靠前、开始与结束两段规则写得一模一样、结束年份早于开始年份，保存时当场就会指出来。

换算条件可以存成**换算方案**反复执行，每次执行留下一条带明细的**换算结果**。时区档案被方案与结果引用着，删除前会先列清引用情况，由操作者选择把引用改挂到别的档案、或确认后连同引用一起清掉，不会留下指向空档案的引用。

数据全部存在本机的数据文件里，不连数据库，也不调用任何外部服务。

## 技术栈

- 后端：Node.js（>=18）与 Express，前后端同一个进程
- 前端：原生 HTML、CSS 与 JavaScript，页面文件由后端静态目录直接提供，没有构建步骤
- 存储：本地 JSON 文件 `data/db.json`

## 启动方式

```bash
npm install
npm start
```

启动后打开页面地址：<http://localhost:5126>

端口固定为 `5126`，如需临时改动可在启动前设置环境变量 `PORT`。测试或另开一份数据时可以设置 `TP126_DATA_DIR` 指向别的目录，服务会在该目录下读写 `db.json`。

跑测试：

```bash
npm test
```

## 页面怎么用

1. 时区档案区列出时区名称、显示名称、标准偏移、是否实行夏令时、夏令时偏移、切换规则、生效年份、备注与当前被引用的条数；可以按是否实行夏令时筛选，也能按名称、显示名或备注搜索
2. 点新建档案填上时区名与偏移；实行夏令时的档案还要把夏令时偏移与开始、结束两段切换规则（第几个星期几的几点几分）以及生效年份填上
3. 换算台选好日期、时刻与来源时区，点换算一遍，页面列出每个已登记时区的当地日期、当地时刻、星期、与来源是否同一天、偏移以及跟来源时区差多少
4. 点「把当前换算条件存为方案」把换算台的日期、时刻与来源时区存成换算方案；在换算方案区点「执行并存结果」可反复执行，每次按当前登记的档案算出一份带明细的结果，留在换算结果区随时查看或删除
5. 任何一步不成立时，页面顶部给出说明，并尽量把问题标到对应的输入项上

## 引用与删除口径

时区档案会被两个地方引用，删除前必须先处理引用：

- **换算方案**：方案把某个档案选作来源时区
- **换算结果**：结果的来源时区是某个档案；此外每份结果的明细行里还会出现换算时登记在册的每个档案

档案每行的「引用 N」按钮与删除时弹出的面板都能单独查看引用，分三类列出：被换算方案引用、作为换算结果的来源、出现在结果明细里。三类各自列出具体条目，顶部的总条数等于三类条数之和，计数与列表严格对得上。

删除规则：

- 档案**没有任何引用**时可直接删除
- **有引用时不允许裸删**，接口返回 `409 ZONE_IN_USE`；删除弹窗列出全部引用，并给出两种处理方式：
  - **改挂到别的档案**：引用它的方案改选新档案；以它为来源的历史结果按保存的基准 UTC 时刻、用新档案把全部明细重算一遍（同一绝对时刻不变，只是换了来源时区的表示）；其它结果明细里它那一行换成新档案
  - **连同引用一起清掉**（需勾选确认）：引用它的方案整条删除；以它为来源的结果整条删除；其它结果只移除它那一行明细，结果本身保留
- 两种方式都在一次操作里完成：所有校验在改动前做完，内存中的改动集中完成后才落一次盘；中途任何一步失败都不会写文件，档案仍在、方案与结果也保持原样，不会落到删了一半的状态
- 删除换算方案会把由它执行出来的结果一并删掉

## 换算口径

- 换算按登记的标准偏移进行：先把输入的当地时刻减去来源时区的标准偏移得到基准时刻，再逐个时区加上各自的偏移
- 每个时区的当地日期与时刻都由基准时刻加上该时区的偏移算出，日期是否翻到前一天或后一天按公历日比较
- 与来源时区的时差按两边偏移的差值给，整小时只写小时，带分钟的把分钟也写出来
- 结果按偏移从小到大排列，来源时区那一条在页面上会标出来
- 档案里登记了夏令时规则不等于换算时已经计入夏令时，规则本身如何落到具体日期上需要另行处理

## 登记口径

- 时区名称写成地区加城市，例如 `Asia/Shanghai`；基准时可以写 `UTC`；最长 40 个字符，不能重复
- 标准偏移与夏令时偏移都按整数分钟登记，范围是 -720 到 840，带半小时或三刻的地区直接写对应的分钟数（例如东五区半写 330、加德满都写 345）
- 实行夏令时的档案必须填夏令时偏移，且要比标准偏移更大（数值上更靠前）
- 切换规则分开始与结束两段，每段写清月份、第几个星期（一到四或者最后一个）、星期几、小时与分钟
- 生效年份填 1900 到 2100 之间；结束年份留空表示至今有效，已经停止实行夏令时的地区要把结束年份填上
- 备注用来写这条档案需要留意的地方，最长 200 个字符

## 数据存储

所有数据写在 `data/db.json`，结构为 `{ "zones": [...], "schemes": [...], "results": [...] }`：`zones` 是时区档案，`schemes` 是换算方案（日期、时刻、来源时区 id），`results` 是执行方案留下的结果（来源快照、基准 UTC 时刻与每个档案的明细行）。落盘时先把内容写进同名临时文件，再用改名的方式替换正式文件，写入过程中断也不会把数据文件写坏；文件缺失或内容损坏时会自动回落到初始数据。载入时会顺带整理引用：方案与结果引用的档案不在了，对应的方案或结果不会保留，保证库里不留悬空引用。

## 接口一览

| 方法   | 路径             | 说明                                       |
| ------ | ---------------- | ------------------------------------------ |
| GET    | /api/health      | 服务状态检查                               |
| GET    | /api/zones       | 时区档案清单，支持按是否实行夏令时筛选与关键词搜索，每条带 referenceCount |
| POST   | /api/zones       | 新增时区档案                               |
| GET    | /api/zones/:id   | 查看单条档案                               |
| PATCH  | /api/zones/:id   | 修改档案                                   |
| DELETE | /api/zones/:id   | 删除档案；有引用时返回 409，不允许直接删   |
| GET    | /api/zones/:id/references | 查看引用：三类引用清单与计数（总数=三类之和） |
| POST   | /api/zones/:id/delete | 带策略删除：body 为 `{strategy:"reassign",targetId}` 或 `{strategy:"cascade",confirm:true}` |
| POST   | /api/convert     | 把一个时刻换算到所有已登记的时区（即算即看，不落库） |
| GET    | /api/schemes     | 换算方案清单                               |
| POST   | /api/schemes     | 新增换算方案                               |
| GET    | /api/schemes/:id | 查看单条方案                               |
| PATCH  | /api/schemes/:id | 修改方案                                   |
| DELETE | /api/schemes/:id | 删除方案，连同由它执行出的结果一起删       |
| POST   | /api/schemes/:id/run | 执行方案，按当前档案算一遍并把结果落库   |
| GET    | /api/results     | 换算结果清单，可按 `?schemeId=` 过滤       |
| GET    | /api/results/:id | 查看单条结果的完整明细                     |
| DELETE | /api/results/:id | 删除单条结果                               |

接口出错时统一返回 `{ "error": { "code": "...", "message": "...", "field": "..." } }`，其中 `field` 用于让页面把问题标到具体的输入项上。
